What the program does, in one minute

A factory test station writes thousands of log files a day into folders like D:/logs/BURNIN. Each file name contains a product barcode (for example unit1_BC001_log.txt). Once a product has shipped, its logs only need to be kept, not used, so they should move off the busy disk into compact archives where they can still be found by barcode.

Ask SQL Server: which barcodes shipped?→ Find their log files in the source folders→ Move them into monthly archives (2026-08.mochi)→ Record every file in a SQLite index

The hard part is not moving files. It is doing it so that a crash, a power cut or a full disk at any moment never loses a file and never stores one twice. Most of the design follows from that one goal.

The one rule to keep in mind

A log file is always in exactly one of three places: the source folder, the staging folder, or a verified archive. A copy is deleted only after the next place has been checked. Every page of this guide comes back to this rule.

Two languages, one boundary

Python this repository

Decides what to back up and keeps the bookkeeping: config, SQL Server, folder scan, staging, SQLite index, the screen. About 1,200 lines in two files.

Rust MOCHI repository

Knows how to write an archive safely: compression, deduplication, commits that are never half-written, verification. A large, separately tested project.

They meet at a single, narrow point: Python runs mochi.exe --json … as a separate process and reads its JSON answer. There is no shared memory, no library linking, no network. If you can read a command line and a JSON object, you can review the boundary. The full story is on Python ↔ MOCHI (Rust).

For senior reviewers

The process boundary is a deliberate choice over Rust bindings (PyO3): it keeps the Python side free of a compiled extension, lets either side be upgraded alone, and makes MOCHI's own exit codes and error codes the contract. The cost is process start-up per command (a few per month per run) and parsing JSON, both negligible next to disk I/O.

Python in five minutes (for non-Python readers)

You only need these constructs to read every line of this repository.

with lock_run(cfg):           # take the lock
    return _run(cfg, ...)     # ... released here, even if _run raises

with db:                      # SQLite: one transaction
    db.execute("INSERT ...")  # committed at the end, rolled back on error

with X: runs set-up code, then the block, then always runs clean-up, even after an error. Like C#'s using, Java's try-with-resources, Go's defer, or Rust's Drop. On a SQLite connection, with db: means "one transaction" (it does not close the connection).

db = open_index(cfg.db_path)
try:
    return _run_with_index(db, ...)
finally:
    db.close()        # runs whether the try block returned or raised

raise throws an exception, except E as e: catches it. Expected failures are BackupError; the UI shows its message to the operator.

Functions are ordinary values. This is how the UI plugs its drawing code into the logic without the logic knowing anything about screens. Tests use the same trick to replace SQL Server with a fixed list.

with ThreadPoolExecutor(8) as pool:
    job = pool.submit(commit_month, cfg, "2026-08", entries)  # starts on a worker thread
    hashes, head = job.result()                               # waits; re-raises its error here

Several months are committed at the same time on worker threads. Worker threads only run mochi.exe and hash files. SQLite writes and file deletes stay on the main thread, which keeps ordering simple to reason about.

p = subprocess.run([exe, "--json", "list", archive], capture_output=True, text=True)
p.returncode      # mochi's exit code (0 = ok)
p.stdout          # what mochi printed: one JSON object
json.loads(p.stdout)   # -> Python dict

This is the whole bridge to Rust: start a program, wait for it, read its exit code and output.

Words used in this guide

WordMeaning here
BarcodeProduct serial number from SQL Server (serial_no), also found inside log file names.
CandidateA barcode returned by SQL Server for the current date window: its logs may be archived.
Month / volumeYYYY-MM of the barcode's last_update. One archive file per month.
Stagingsource_dir/.staging/: the waiting room between the source folders and the archive.
Manifest.staging/manifest.jsonl: one JSON line per staged file, written and flushed to disk before the file moves.
CommitOne write to a .mochi archive. Either fully there or not at all. Numbered by seq (0, 1, 2, …).
HeadThe newest commit of an archive: what mochi list shows.
BLAKE3A fast cryptographic hash. Two files with the same BLAKE3 have the same bytes. Python and MOCHI compute it the same way, which is how Python checks MOCHI's work.
LOCAL_COMMITTEDThe final state of a run: data written and synced to one local archive. Not a backup by itself; --export makes an independent copy.
DEGRADED (not an error)MOCHI's warning that the data is committed but the operating system did not confirm the folder entry is durable. Always printed on Windows.
