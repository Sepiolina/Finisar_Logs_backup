Staging and the manifest


.staging/manifest.jsonl is a text file with one JSON object per line ("JSON Lines"). Line 1 names the session; every other line is one staged file:


{"scan_session_id": 42}
{"relative_path": "BURNIN/unit1_BC001_log.txt", "source_subfolder": "BURNIN", "barcode": "BC001", "original_size": 10, "volume_name": "2026-08"}
{"relative_path": "ESS/unit2_BC002.txt", "source_subfolder": "ESS", "barcode": "BC002", "original_size": 7, "volume_name": "2026-07"}




FieldMeaning


relative_pathPath below source_dir, with /. Also the path inside the archive and in the index.


source_subfolderThe top folder (BURNIN), even when the file was deeper.


barcodeThe one barcode found in the file name.


original_sizeBytes, from the scan.


volume_nameArchive month YYYY-MM, from the barcode's last_update.




Why JSON Lines

Appending a line never rewrites earlier ones, and a crash can only damage the last line, which read_manifest skips. Lines are written in batches of 2,000 (MANIFEST_BATCH) with one fsync per batch: fewer syncs, same guarantee, because a batch's files move only after its lines are synced.



Inside a .mochi archive


A .mochi file is an append-only chain of commits. Each run adds one commit to each month it touched; earlier commits are never rewritten. The newest commit is the head, and it shows the whole month as it is now.













    

  • Paths inside are <SUBFOLDER>/<path below it>; a later file in an existing folder is added to it, the earlier files stay.
    • 

  • Each file keeps its original modification time (a rename does not change it).
    • 

  • MOCHI compresses (Zstandard) and deduplicates by itself; the backup tool does not configure either.
    • 

  • A commit is published atomically: a reader sees the old head or the new one, never half of a commit.
    •

Useful queries











SELECT e.relative_path, v.path, e.content_hash
FROM scanned_log_entry e
JOIN file_storage_volume v ON v.id = e.file_storage_volume_id
WHERE e.barcode = 'BC001';


Then extract: mochi get E:/archive/2026/2026-08.mochi BURNIN/unit1_BC001_log.txt -C D:/restore (MOCHI checks the hash before writing).


SELECT id, status, query_from_date, query_to_date, total_files_moved, total_errors
FROM scan_session ORDER BY id DESC LIMIT 10;


SELECT volume_name, entry_count, file_size, head_seq FROM file_storage_volume ORDER BY volume_name;




Refused, not changed

open_index refuses an index with another user_version, or the old format's columns (sha256, chunk_start_byte), and leaves it untouched. Move it aside and a new one is created. Silent migration of a bookkeeping database is a classic way to lose track of data.

The backslash trap

In JSON, \b is a backspace and \t a tab. So "E:\backup" silently becomes E: + backspace + ackup. Config refuses any path containing a control character and says to write E:/backup. Test: test_backspace_in_a_path_is_refused.
