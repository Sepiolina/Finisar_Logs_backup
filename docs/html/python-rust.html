Python ↔ MOCHI (Rust)

How the Python code finds the MOCHI engine, talks to it, and checks that it did its job. All of it lives in one section of logs_backup.py, marked # ---- MOCHI.

It is a program, not a library

MOCHI is written in Rust and built into a normal executable, mochi.exe. Python does not load Rust code into its own process. It starts mochi.exe as a child process, exactly like typing a command in a terminal, waits for it to finish, and reads three things back.

What goes in

Only command-line arguments: the command, the archive path, input folders. Nothing is sent on standard input. File data never passes through Python: MOCHI reads the staged files from disk itself.

What comes out

An exit code (the verdict), one JSON object on standard output (the details), and maybe text on standard error. With --json, MOCHI prints errors as JSON too: {"error": {"code": "…", "message": "…"}}.

Why this is easy to review

Every interaction is something you can reproduce by hand in a terminal. If you doubt what Python sees, run the same command yourself: mochi --json list E:/archive/2026/2026-08.mochi.

Trade-off

A Python extension module (PyO3) would avoid process start-up and JSON parsing, but would tie this tool to one MOCHI build and one Python version, and put a compiled binary inside the Python package. A run here issues about four MOCHI commands per month touched; the cost of starting a process is milliseconds against seconds of disk work. The README calls this out as a deliberate difference from the earlier Rust tool: MOCHI through its command line (mochi --json), not the Rust library.

How Python finds mochi.exe

mochi_places() builds a list of places to try, and check_mochi() tries them in order by running <place> --version. The first one that exits 0 and prints a line starting with mochi wins. Its full path is stored in cfg.mochi so later commands never search again.

Switch places on and off to see which one is used:

mochi_places(configured) the list, in code
if configured and configured != "mochi":      # "mochi" (old example config) means: find it
    return [str(configured)]
here = program_dir()                            # .exe folder when frozen, else this file's folder
places = [*registry_mochi(), shutil.which("mochi"),
          setup and Path(setup) / "MOCHI" / "bin" / MOCHI_EXE,
          Path.home() / ".cargo" / "bin" / MOCHI_EXE, here / MOCHI_EXE,
          here.parent / "MOCHI" / "target" / "release" / MOCHI_EXE,
          here.parent / "mochi" / "target" / "release" / MOCHI_EXE]
return list(dict.fromkeys(str(p) for p in places if p))   # keep order, drop repeats

registry_mochi() returns [] on anything but Windows. It reads the default value of Software\Microsoft\Windows\CurrentVersion\App Paths\mochi.exe (current user, then machine) and Software\The MOCHI Project contributors\MOCHI (the install folder, to which it adds bin\mochi.exe). Tests pass a fake registry object instead of winreg.

When no place works and only mochi-desktop.exe is installed, the error adds a hint: that setup version did not include the command-line program.

Gotcha seen in practice

The --version check matters: a file named mochi.exe that is the wrong program, or a build that cannot start, is skipped rather than trusted. And on a PC where the MOCHI setup is installed, the registry entry is found before PATH: a test that wants "not found" must switch the registry lookup off (test_mochi_is_found_without_a_config_path does).

Where mochi.exe comes from

The MOCHI Windows setup 0.9.15 or newer installs bin\mochi.exe next to the desktop app and registers it under App Paths. Nothing to configure: place 2 or 3 finds it.

In a MOCHI checkout (Rust 1.89+; the repo pins 1.91 in rust-toolchain.toml):

cargo build --release -p mochi-cli      # -> target/release/mochi(.exe)

If the checkout sits beside this repo (D:/GitHub/MOCHI next to D:/GitHub/Finisar_Logs_backup), place 9 finds it. cargo install --path crates/mochi-cli puts it in ~/.cargo/bin (place 7).

"mochi": "C:/tools/mochi-0.9.15/mochi.exe"

Write Windows paths with /: in JSON, "C:\tools" contains \t, a tab character. Config refuses paths with control characters for this reason.

Every command Python sends

All calls go through one function, mochi(cfg, *args), which always adds two options:

[cfg.mochi, "--json", "--no-local-history", *args]
--json
Machine-readable output: one JSON object on standard output, errors included.
--no-local-history
MOCHI normally records each archive's last-seen head and its check results in a per-user state folder (%LOCALAPPDATA%\mochi). This tool keeps its own record in SQLite, so it asks MOCHI to record and consult nothing there.

Who: check_mochi, once per run (and in --check-sql). Not through mochi(): no --json.

$ mochi --version
mochi 0.9.15

Accepted when the exit code is 0 and the output starts with mochi . The UI shows mochi 0.9.15 (C:\…\mochi.exe).

Who: commit(cfg, month). create when the month's archive does not exist yet, append when it does. Inputs are the folders .staging/<month>/<SUB>; MOCHI names each input after its last part, so .staging/2026-08/BURNIN becomes BURNIN/ in the archive, and an append merges into the existing BURNIN/.

$ mochi --json --no-local-history append E:/archive/2026/2026-08.mochi D:/logs/.staging/2026-08/BURNIN D:/logs/.staging/2026-08/ESS
{"command": "append", "archive": "E:/archive/2026/2026-08.mochi", "status": "…",
 "seq": 1, "commit_id": "9f2c…", "durability": "directory_unconfirmed",
 "durability_note": "directory flush ran, but Windows does not document it as durable",
 "added": {"files": 2, "directories": 0, "bytes": 3125}, "exit_code": 2, …}

Python reads: only durability. If it is not "durable", it logs 2026-08: DEGRADED (not an error): <durability_note>. Exit 2 is accepted: the data is committed.

Who: head_files(cfg, archive), after every commit, and before a commit when resuming.

$ mochi --json --no-local-history list E:/archive/2026/2026-08.mochi
{"schema": "…", "archive_id": "…", "seq": 1, "commit_id": "9f2c…",
 "entries": [
   {"path": "BURNIN", "kind": "directory", …},
   {"path": "BURNIN/unit1_BC001_log.txt", "kind": "file", "size": 10,
    "content_hash": "c3f1…64 hex digits…"}, …]}

Python reads: {path: content_hash} for entries whose kind is "file", plus (seq, commit_id), which are stored in SQLite as the archive's head.

Who: commit_month, last step before a month counts as done.

$ mochi --json --no-local-history verify E:/archive/2026/2026-08.mochi --level content

Python reads: only the exit code. 0 or 2 passes; 1 (a verification failure) or anything else raises, and the month stays in staging. MOCHI's report has more detail (per-dimension results); it is visible by running the command by hand.

$ mochi --json --no-local-history append E:/archive/2026/2026-08.mochi …
{"error": {"code": "UNCOMMITTED_TAIL", "message": "…"}}       exit code 3

Python does: raises BackupError("mochi append E:/…: exit 3 {'code': 'UNCOMMITTED_TAIL', …}"). If the output is not JSON (a crash, a clap argument error), it uses the text from standard error instead. The month's files stay in staging.

Exit codes: MOCHI's verdict and Python's reaction

ExitMOCHI meansPython does
0Done, nothing to report.pass continue
2Done, with a warning: for writes, data is committed but the folder entry is not confirmed durable (always on Windows in MOCHI 1.0); for checks, a dimension is unknown or degraded.pass continue; log DEGRADED (not an error) for writes
1A verification violation: integrity failure, damaged frame, no valid head, unresolved tail…fail raise; month stays in staging
3Operational error: bad argument, destination exists, uncommitted tail, I/O error…fail raise; month stays in staging
4Refused: a feature this build does not support.fail raise; month stays in staging

Source: MOCHI docs/c14-cli.md and crates/mochi-cli/src/exit.rs. In Python: if p.returncode not in (0, 2): raise BackupError(...).

Trust, but check: the BLAKE3 handshake

A non-zero exit is not the only thing that can go wrong. What if MOCHI stored the wrong bytes, or missed a file? Python checks the result with its own computation, independent of MOCHI's code paths:

  1. While MOCHI commits, Python hashes every staged file with the blake3 library (worker threads, 500 files per task).
  2. After the commit, mochi list gives MOCHI's content_hash for every file in the head.
  3. Every staged path must be in the head with the same hash. One mismatch fails the month.
  4. Then mochi verify --level content re-reads the archive end to end.
Why the two hashes can be compared

MOCHI uses domain-separated BLAKE3 for its internal hashes (chunks, objects, commit IDs: BLAKE3(separator ‖ data)), but its file content hash is plain BLAKE3(file bytes) (crates/mochi-format/src/digest.rs, scope FileContent). That is exactly what Python's blake3.blake3(data).hexdigest() and the b3sum tool print, so anyone can check a file against the index by hand.

Rust words, decoded

crate = package/module. cargo = Rust's build tool and package manager (like npm or pip). --release = optimized build, output in target/release/. clap = the library MOCHI uses to parse command-line arguments; when arguments are invalid it prints plain text to standard error and exits 3, which is why Python falls back to standard error when the output is not JSON.

Check yourself

MOCHI exits with code 2 after an append on Windows. What happens to the month?

Exit 2 for a write means "committed, with a durability warning". On Windows MOCHI 1.0 always reports the folder entry as unconfirmed. The month is still listed, hash-checked and verified before anything is deleted.

"mochi": "mochi" is in an old config.json. What does Python do?

mochi_places: if configured and configured != "mochi". The old example config had this value, so it means "find it".
