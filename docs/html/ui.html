UI ↔ logic: backup_ui.py

backup_ui.py draws the screen. logs_backup.py decides everything. This page shows the small, strict contract between them, and why it makes the code safer to review.

The pattern: logic knows nothing about screens

logs_backup.py logic

  • Reads config, queries, scans, moves, commits, verifies, indexes, deletes.
  • Never prints a progress bar or asks a question.
  • Tells the outside world what it is doing by calling functions it was given.
  • Runs alone too: python logs_backup.py (scheduled tasks).

backup_ui.py screen

  • Parses options, finds the config, sets up logging, asks for the password.
  • Calls one function: lb.run(cfg, dry_run, report=…, confirm=…).
  • Draws what it is told; returns the operator's yes/no.
  • Cannot move, commit or delete a file: it has no code that does.
Review consequence

For a safety review you only need logs_backup.py. A change to backup_ui.py can make the screen wrong, but it cannot lose a file, as long as it keeps calling only run(), export(), check_mochi(), check_sql() and send_email(). A change that adds file operations to the UI breaks the pattern and should be questioned.

Name for this

This is the callback (or "dependency injection") pattern: instead of the logic importing a screen library, the caller passes in small functions. The tests use the same door: they pass a list instead of SQL Server, and a confirm that says no.

The contract, in full

summary = lb.run(cfg, candidates_fn=None, dry_run=False, report=quiet, confirm=None)
ParameterTypeMeaning
reportreport(step, message="", done=0, total=None)Progress only. step is resume, query, scan, stage or commit (export for lb.export). total=None = not known yet (spinner). Default quiet does nothing. Its return value is ignored.
confirmconfirm(volumes) -> boolCalled once, after the scan and before any file moves, with {"2026-08": (barcodes, files, bytes), …}. False → status="cancelled", nothing moved, nothing written to the index. Not called when nothing matched. None = do not ask.
dry_runboolQuery and scan only; returns status="dry_run". A missing mochi is only a warning.
candidates_fnfn(date_from, date_to) -> [(barcode, last_update)]Replaces the SQL Server query. The UI never sets it; tests and bench.py do.

Returns a plain dict. Raises BackupError (expected problems, message meant for the operator) or any other exception (bugs, disk errors).

How the two files find each other

import logs_backup as lb      # first line of logic in backup_ui.py

Python looks for logs_backup.py in the folder of the script it is running, so the two files must sit side by side. That is the whole connection: an ordinary import, then ordinary function calls in the same process. run_backup.bat just runs backup_ui.py with .venv\Scripts\python.exe if it exists, else python.

build_exe.bat runs PyInstaller on backup_ui.py. PyInstaller follows the imports and packs Python itself, both .py files and the libraries (rich, pymssql with its FreeTDS, blake3) into one file. At start-up the .exe unpacks to a temporary folder and runs from there.

That is why program_dir() exists: in the .exe, __file__ points into the temporary folder, so "next to the program" must use sys.executable (the .exe's real folder) instead. mochi.exe is not packed inside; it is found at run time like any other install.

find_config(): the path given on the command line, else config.json in the current folder, else config.json next to the program (the .exe's folder when frozen). Double-clicking the .exe starts it in its own folder, so a config.json beside it is found. backup.log is written next to whichever config was used.

A developer wants the UI to delete empty staging folders after a run. Where should that code go?

File operations belong to the logic, where they are tested and ordered with the safety rules. The UI only draws.
