How the algorithm works

Instead of a regular expression per barcode (slow with 100,000 barcodes) or an Aho-Corasick automaton (an extra library), find_barcodes lists every place a barcode may start (position 0 or after a delimiter) and may end (before a delimiter or at the end), and looks up each substring between them in a Python set (a hash table). File names are short and have few delimiters, so this is a handful of lookups per file, whatever the number of barcodes.

The date window

date_range set in configExactly that rangeRe-running a period on purpose; the tests use it.
First run everEverything before today − lookback_daysCatch up on the whole history.
Later runsFrom (last successful end date − 1 day) to today − lookback_daysCovers any gap since the last success, whether runs are daily or monthly; the 1-day overlap catches late rows. Barcodes seen before are not recorded twice (UNIQUE(barcode, last_update)).

Check yourself

Why is each manifest line written and fsync'ed before its file is renamed, not after?

If the file moved first and the power went out before its line was written, staging would hold a file nobody knows about. Writing first means the worst case is a listed file that never moved, which the resume skips harmlessly. MOCHI never reads the manifest; only Python does.

A run crashes right after mochi append succeeded but before SQLite was updated. What does the next run do with those files?

That is commit_month(..., resume=True). Deleting without verifying and indexing would break the rule "deleted only after the next place is checked".
